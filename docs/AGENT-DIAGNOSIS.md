# AI 诊断助手（会话式 Agent）需求方案

> 状态：**已确认，待开发**（2026-08-19 老板确认，暂不开发）
> 背景：现有 executor 通过 kubeconfig 只能做「资源层」操作（重启 pod/describe/rollout 等），集群/节点层面的问题能自动处理；但「应用层」问题（应用报错、逻辑/配置/性能）够不着。本方案增加会话式 AI 诊断 agent 兜底。

## 老板拍板的决策（2026-08-19）

1. **部署形态**：平台侧扩展——executor 加 `ExecInPod`（kubectl exec 等价），直接进容器，**不往集群装任何东西**
2. **能力边界**：**只诊断，不做修复**（修复=改代码，平台暂无代码功能）；输出诊断结果 + 处理意见
3. **入口形态**：**单独会话（对话式）**，不同用户隔离；诊断闭环确认后**落盘知识库**

## 架构（零新增组件，全平台侧）

| 组件 | 改动 |
|---|---|
| k8s-executor | 新增 `ExecInPod` gRPC（client-go remotecommand，等价 kubectl exec），只读诊断命令 |
| ai-service | 新增对话式诊断接口：多轮上下文 + 工具调用循环（AI 自主决定下一步） |
| api-server | 新增会话 API：会话隔离 + RBAC 过滤可见集群 |
| frontend | 新增「AI 诊断助手」页，对话式聊天 UI |

## 诊断工具集

1. **容器内只读命令**：ps / env / cat 配置 / ss·netstat / df / 进程详情等（白名单 + 强制只读）
2. **应用日志**：ES（现有 es_client）+ 容器 stdout
3. **Pod describe + events**（现有能力复用）
4. **资源指标**（现有 pod_metrics 复用）

## 对话闭环流程

1. 用户发起：选集群/命名空间/pod + 描述问题
2. AI 规划 → 调工具诊断（多轮追问）
3. 返回：诊断结果 + 处理意见
4. 用户按意见处理
5. 用户确认「处理完成」→ 结构化落盘知识库（现象/根因/处理意见/实际处理）
6. 后续同类型告警自动处理可直接命中（复用 rag 检索，相似度≥0.9 直接走历史方案）

## 隔离与安全

- 会话按 user_id 隔离，只能看到自己权限内的集群（复用现有 RBAC）
- 命令白名单 + 强制只读（防误操作改容器）+ 全量审计留痕（谁/何时/哪个 pod/执行了什么）
- 镜像无 shell 兜底：退化为日志 + describe 诊断，不硬闯

## 开发步骤

1. executor：ExecInPod + 命令白名单（Go）
2. ai-service：对话诊断 + 工具循环（Python）
3. api-server：会话/消息 API + RBAC
4. frontend：对话页
5. 闭环落盘 + 全链路联调
