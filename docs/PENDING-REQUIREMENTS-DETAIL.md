## 2. N4 健康检查 readiness / liveness 拆分 ✅

**现状**：`k8s/deployments.yaml` 里 api-server 的 liveness 与 readiness **都指向同一个 `/health`**；ai-service 只有 `/health`。

**需求**
- `/health`（liveness）：只判进程存活，**不查 DB/Redis/下游**，永远快速返回（避免依赖抖动导致被 kill）
- `/ready`（readiness）：判依赖就绪（DB/Redis 可连通），不通则不接流量
- 同理 ai-service 拆 `/live` + `/ready`
- k8s manifest 对应改指向

**验收**：断掉 DB 时 `/health` 仍 200、`/ready` 503，Pod 不被重启。
**预估**：0.5 天。

## 3. N5 异常 Pod 重启原因 AI 诊断 + 告警通知 ✅

**现状**：executor 已采集 Pod RESTARTS 计数，但**重启没有触发任何诊断或告警**。

**需求**
- 检测 **RESTARTS 计数增加**，且原因属 **OOMKilled / 探针失败（Liveness/Readiness probe failed）** 的重启（**排除手动重启**、排除正常滚动发布）
- 命中 → **自动发起 AI 诊断**（复用现有诊断链路），产出重启原因结论
- 诊断结果 → **发告警通知**（走通知策略）
- **不生成审批单、不走审批**（老板 09-18 明确）

**实现要点**
- executor：Pod 快照对比上一次 RESTARTS，识别增量 + `lastState.terminated.reason`；过滤手动/发布（可用 `kubectl rollout history` 或 Pod 创建时间/注解判断）
- api-server：接收重启事件 → 写一条 alert（新增 fault_type 如 `PodRestartOOM`/`PodProbeFail`）→ 自动处理链路跑 AI 诊断 → 通知；`manual_required=False` 且跳过审批
- 前端：告警列表能看到该类告警 + 诊断结论

**验收**：造一个 OOMKilled 重启 → 自动出告警 + AI 结论 + 通知，无审批单。
**预估**：1.5 天。

## 4. N6 DB 报错告警接入告警策略 ✅

**现状**：`db_collector` 采集指标 + 连接状态，但**数据库报错（连接失败等）不产生告警**，不进告警策略/通知。

**需求**：数据库出现报错（连接失败、认证失败、连接池耗尽等）→ **生成告警**，并**统一走现有告警策略**（分派、通知、静默/维护窗口全部复用）。

**实现要点**：DB 健康采集失败/指标越限 → 写 `alerts`（source=db，fault_type 如 `DBConnFailed`）→ 进 alert_auto_service 链路。
**验收**：故意填错 DB 密码 → 产生告警 + 按策略通知。
**预估**：1 天。

## 5. N7 日志源自定义（多实例）✅

**现状**：ES 只有**全局单一配置**（env），日志告警规则绑死这一个源。

**需求**
- 支持**自定义配置多个日志源**：名称 / ES 地址 / 索引 / 账号密码（不绑环境）
- 日志告警规则**可选日志源**（不选=默认全局源）
- **兼容现有全局 ES**：存量规则继续可用，不需要迁移动作

**实现要点**：新增 `log_sources` 表 + CRUD API + 前端「日志源管理」页；`log_alert` 规则加 `log_source_id`（空=全局）；日志查询/告警扫描按源取 client；密码加密存储（复用现有加密）。
**验收**：配 2 个源，规则分别绑不同源，各自能查日志并触发告警；旧规则不受影响。
**预估**：2 天。

## N1 工单（平台内部工单）✅ 已定稿（老板 09-20 拍板）

**老板口径**：工单**只是平台内部的**；外部系统**只是接入**（供外部查询/创建，不做双向状态同步）；**报警和工单机制不变**。

**需求**
- 新增平台内部工单：告警/审批可「转工单」，也可手动建单
- 工单独立于告警/审批状态机，**不改动现有告警与审批机制**（告警状态、审批流程、自动处理链路一律不动）
- 提供**接入接口**给外部系统（只读/创建），不要求外部回写状态

**数据模型（新增 2 表）**
- `tickets`：id / ticket_no / title / description / source(alert|approval|manual) / alert_id / approval_id / cluster_id / namespace / resource_name / priority(low|medium|high|urgent) / status(open|processing|resolved|closed) / assignee_id / created_by / resolved_at / closed_at / created_at / updated_at
- `ticket_comments`：id / ticket_id / user_id / type(comment|action) / content / created_at

**状态机**：open(待受理) → processing(处理中) → resolved(已解决) → closed(已关闭)；open/processing 可直接 closed；每次流转写一条 action 留言

**接口**
- `POST /api/v1/tickets`（手动建单）｜`POST /api/v1/tickets/from-alert/{alert_id}`｜`POST /api/v1/tickets/from-approval/{approval_id}`
- `GET /api/v1/tickets`（分页 + 状态/优先级/来源/集群筛选）｜`GET /api/v1/tickets/{id}`
- `PATCH /api/v1/tickets/{id}`（状态/优先级/处理人/标题描述）｜`POST /api/v1/tickets/{id}/comments`
- `POST /api/v1/tickets/{id}/assign`
- 外部接入（本期最小）：`GET /api/v1/tickets`、`POST /api/v1/tickets` 走 API Token（新增 `api_tokens` 或复用内部 token 机制）

**权限**：可见范围按项目/集群权限收敛；`operate`+ 可处理/流转；`manager`/admin 可关闭与删除；DB 类工单按 db 权限

**通知**：转工单 / 指派 / 状态变更 → 走现有站内消息与 IM 通道（复用通知层，不新建）

**前端**：新增菜单「工单」（工单处理合并页）；列表 + 详情抽屉；告警详情/审批详情加「转工单」按钮

**验收**：告警转工单后告警状态不变；工单可指派/流转/留言/关闭；外部 token 可创建+查询；权限边界正确
**预估**：3 天

## N3 诊断分离（集群故障 / 应用故障 / 数据库故障）✅ 已定稿（老板 09-20 拍板）

**老板口径**：三个诊断要**分开** —— ① 应用故障 ② 数据库故障 ③ 集群故障。

**现状问题**：三个入口存在但**没真正分离**——「故障诊断」是**告警全量列表**（集群/节点/应用/Pod 混在一起），知识库与报告也不带诊断类别，无法按类别隔离。

**需求：三个独立诊断模块**

| 模块 | 目标对象 | 数据源 | 覆盖故障 | 知识库类别 |
|---|---|---|---|---|
| **集群故障诊断** | 集群 / 节点 | 节点状态(NotReady/压力)、集群资源水位、QuotaSnapshot | NodeNotReady、节点磁盘/内存压力、集群组件异常 | `cluster` |
| **应用故障诊断** | 集群+ns+Pod/工作负载 | Pod 状态/事件/日志/指标（现有 /agent 会话式诊断 + 应用类告警） | CrashLoopBackOff、OOMKilled、ImagePull、探针失败、PodRestart | `app` |
| **数据库故障诊断** | DB 连接 | DB 指标/慢SQL/连接状态（现有 /diagnostic） | 连接失败、连接数告警、慢查询、缓存命中率异常 | `db` |

**分离内容**
1. **入口分离**：三个独立菜单/页面（告警处理下的「故障诊断」拆为「集群故障诊断」；「应用诊断」「数据库诊断」独立保留）
2. **数据分离**：告警/诊断记录带 `diag_category`（cluster|app|db）；每个诊断页只显示本类别
3. **知识库分离**：`knowledge_entries` 加 `diag_category`，检索按类别过滤（AI 诊断复用知识库时不跨类）
4. **报告分离**：`diagnostic_reports` 按类别分区展示
5. **权限分离**：集群/应用走集群+ns 权限，数据库走 db 权限（现有）

**实现要点**
- 新增故障类型 → 类别映射表（`fault_type` → cluster/app/db），落 `Alert.diag_category`
- `fault_diagnosis.py` 列表按类别过滤；新增 cluster 类目标选择器
- 迁移：`alerts.diag_category` + `knowledge_entries.diag_category`（历史数据按 fault_type 回填）
- 前端：菜单调整 + 三页各自的筛选/目标选择 + 报告分区

**验收**：集群类告警只出现在集群故障诊断、应用类只在应用诊断、DB 只在数据库诊断；知识库检索按类别不串；历史数据已回填
**预估**：2.5 天
