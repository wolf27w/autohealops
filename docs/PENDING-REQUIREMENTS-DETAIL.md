## 1. 仪表盘 v2（改造现有 `/dashboard`）✅

**现状**：`/dashboard` 仍是旧大屏（`Screen embedded`）；`StatsDashboard.tsx` 是 9-12 老版；后端 `GET /stats/dashboard` 只有第一版聚合。

**需求（6 段布局）**
1. **顶部栏**：项目筛选 ｜ 集群筛选 ｜ 时间范围 ｜ 刷新按钮 ｜ **全局健康分** ｜ 平台健康（右上角小标）
2. **KPI 行 7 项**：集群数 ｜ 活跃告警 ｜ 自动处理 ｜ 待人工 ｜ DB 异常 ｜ 成功率 ｜ MTTR
3. **告警趋势**（折线/堆叠面积，随筛选时间范围）+ **AI 诊断结果分布**（环形：可自愈/需审批/需人工/诊断失败）
4. **实时告警流**（pending/awaiting_approval 滚动）+ **Top 告警类型**（条形，按 fault_type）
5. **异常 Pod Top N**（表格）+ **数据库健康概览**（各 DB 连接状态+指标）
6. **自动处理动作统计·时间线**（自愈/重启/伸缩/回滚，时间线最近 6 条）+ **集群资源水位 Top**（CPU/内存/Pod 数，点击进集群）

**口径（已定）**
- 自动处理 = **近一年累计**（自愈+重启+伸缩+回滚）；其余 KPI 为当前态，成功率/MTTR 随时间范围
- 异常 Pod = **有告警的 Pod（含刚重启）**
- 全局健康分 = 集群健康 40% + 活跃告警 30% + DB 健康 30%（0~100）
- 项目筛选按「项目绑定的集群+命名空间」过滤，**不与集群筛选联动**
- **移除**「项目健康评分」；项目不做告警
- 平台健康只在右上角显示（k8s 探针探活），**不单独做模块**

**性能**：前端轮询 5s，后端缓存 15s（现 15s/30s）

**实现要点**：重写 `GET /stats/dashboard`（新增趋势分桶、AI 结果分布、Top 类型、动作统计/时间线、资源水位、健康分）+ 新增 `StatsDashboard`/`Dashboard` 重写 + `/screen` 大屏保留不动。

**验收**：7 项 KPI 数字与库一致；筛选切换数据联动；健康分可复算；5s 刷新不闪屏。
**预估**：后端 1 天 + 前端 1.5 天。

## 2. N4 健康检查 readiness / liveness 拆分 ✅

**现状**：`k8s/deployments.yaml` 里 api-server 的 liveness 与 readiness **都指向同一个 `/health`**；ai-service 只有 `/health`。

**需求**
- `/health`（liveness）：只判进程存活，**不查 DB/Redis/下游**，永远快速返回（避免依赖抖动导致被 kill）
- `/ready`（readiness）：判依赖就绪（DB/Redis 可连通），不通则不接流量
- 同理 ai-service 拆 `/live` + `/ready`
- k8s manifest 对应改指向

**验收**：断掉 DB 时 `/health` 仍 200、`/ready` 503，Pod 不被重启。
**预估**：0.5 天。

## 3. N5 异常 Pod 重启原因 AI 诊断 + 告警通知 ✅

**现状**：executor 已采集 Pod RESTARTS 计数，但**重启没有触发任何诊断或告警**。

**需求**
- 检测 **RESTARTS 计数增加**，且原因属 **OOMKilled / 探针失败（Liveness/Readiness probe failed）** 的重启（**排除手动重启**、排除正常滚动发布）
- 命中 → **自动发起 AI 诊断**（复用现有诊断链路），产出重启原因结论
- 诊断结果 → **发告警通知**（走通知策略）
- **不生成审批单、不走审批**（老板 09-18 明确）

**实现要点**
- executor：Pod 快照对比上一次 RESTARTS，识别增量 + `lastState.terminated.reason`；过滤手动/发布（可用 `kubectl rollout history` 或 Pod 创建时间/注解判断）
- api-server：接收重启事件 → 写一条 alert（新增 fault_type 如 `PodRestartOOM`/`PodProbeFail`）→ 自动处理链路跑 AI 诊断 → 通知；`manual_required=False` 且跳过审批
- 前端：告警列表能看到该类告警 + 诊断结论

**验收**：造一个 OOMKilled 重启 → 自动出告警 + AI 结论 + 通知，无审批单。
**预估**：1.5 天。

## 4. N6 DB 报错告警接入告警策略 ✅

**现状**：`db_collector` 采集指标 + 连接状态，但**数据库报错（连接失败等）不产生告警**，不进告警策略/通知。

**需求**：数据库出现报错（连接失败、认证失败、连接池耗尽等）→ **生成告警**，并**统一走现有告警策略**（分派、通知、静默/维护窗口全部复用）。

**实现要点**：DB 健康采集失败/指标越限 → 写 `alerts`（source=db，fault_type 如 `DBConnFailed`）→ 进 alert_auto_service 链路。
**验收**：故意填错 DB 密码 → 产生告警 + 按策略通知。
**预估**：1 天。

## 5. N7 日志源自定义（多实例）✅

**现状**：ES 只有**全局单一配置**（env），日志告警规则绑死这一个源。

**需求**
- 支持**自定义配置多个日志源**：名称 / ES 地址 / 索引 / 账号密码（不绑环境）
- 日志告警规则**可选日志源**（不选=默认全局源）
- **兼容现有全局 ES**：存量规则继续可用，不需要迁移动作

**实现要点**：新增 `log_sources` 表 + CRUD API + 前端「日志源管理」页；`log_alert` 规则加 `log_source_id`（空=全局）；日志查询/告警扫描按源取 client；密码加密存储（复用现有加密）。
**验收**：配 2 个源，规则分别绑不同源，各自能查日志并触发告警；旧规则不受影响。
**预估**：2 天。

## 6. N8 统一告警通知策略（全平台一份）✅

**现状**：集群告警与日志告警的通知配置**是两套**（各自策略/渠道）。

**需求**：集群告警 + 日志告警 **全部走同一套告警通知策略**（全平台统一一份），分级/静默/维护窗口/渠道模板统一。

**实现要点**：合并通知配置入口；告警写入时统一调用同一通知分发层；保留按「告警类型/来源」做规则分流的扩展点。
**验收**：一份策略同时生效于集群告警与日志告警。
**预估**：1.5 天（依赖 N7 落地后再做更顺）。
