# 审计报告通用规范（所有报告必须遵守）

## 硬性约束
- **只读审计**：不得修改业务代码、配置、Dockerfile、Compose、K8s YAML、依赖、Git 分支。
- 不得安装/升级依赖，不得连接生产环境，不得执行数据库写操作。
- 结论必须来自真实源码；禁止按目录名/注释/README/路由存在推断功能已实现。
- 每条结论尽量给出：文件路径 + 行号、类/函数名、API 路由、表/模型、调用链、判断依据。
- 无法确认的写「暂时无法确认」并说明卡点，不得编造。

## 功能状态标签（每个功能必须带一个）
- `已实现（有代码依据）`
- `部分实现`
- `仅前端实现`
- `仅后端接口实现`
- `有接口但业务逻辑不完整`
- `完全未实现`
- `暂时无法确认`

## 问题条目格式（每个问题必须用这个格式，不得省略字段）
```
问题编号：<模块前缀>-<序号，如 K8S-01>
问题名称：
问题等级：P0 / P1 / P2 / P3
所属模块：
问题描述：
代码位置：<相对路径:行号>
涉及函数或类：
调用链：
根本原因：
可能影响：
修改建议：
验证方法：
是否需要立即处理：是 / 否
```

## 等级定义
- P0：严重安全问题（可越权/可绕过审核/凭据泄露/未授权执行）或核心功能不可用
- P1：重要功能缺陷、重要安全弱点、关键链路缺失
- P2：一般缺陷、架构/可维护性问题
- P3：优化建议

## 报告结构建议
1. 结论摘要（3~8 条，带数字）
2. 证据与实现细节（按子模块）
3. 功能状态清单（表格：功能 / 状态 / 证据文件:行 / 备注）
4. 问题清单（按等级排序，用上面的格式）
5. 无法确认事项
6. 审计方法与覆盖范围（读了哪些文件/目录，哪些没读，为什么）

## 写作要求
- 中文，结论先行，避免空话。
- 引用代码时只摘关键 3~15 行，带路径和行号。
- 不确定的数字不要写死，写「约」或给出统计命令。
