# 19 · 能力缺口清单（按未来产品三阶段）

> 输入：`docs/architecture/audit/01~17` + 复核源码（HEAD `b3b9f03`）。与 `18-existing-capabilities.md` 互为对照：18 回答"现在有什么"，19 回答"要去哪、还差什么"。
> 每条缺口给五项：**缺口 / 现状证据 / 影响 / 依赖的前置能力 / 建议阶段**。
> 阶段定义（按产品目标，不是按工作量）：
> - **第一阶段**：平台化底座——统一身份、多项目多角色、真隔离、强制审批、可审计、可 HA。
> - **第二阶段**：研发闭环——代码仓 → CI/CD → 版本定位 → AI 生成修复 → 测试/构建/发布/验证。
> - **第三阶段**：安全左移——漏洞/代码/依赖/镜像扫描 → AI 风险分析 → 选择性修复。
> 标注：`完全未实现` / `有预留（证据）` / `部分基础`。

第一阶段（底座，建议 3 个迭代）

  └─ 波次 C（P0/P1，2 个迭代，工作量最大）

  S2-1 仓库接入 ──> S2-3 版本→代码 ──> S2-4 AI 代码级修复

**三条排期判断：**
1. **波次 A 全是"小改动、堵大口子"**：密钥分层、内部端口鉴权、MCP 收口、DB 禁自批——四项加起来的工作量小于"做一个新功能模块"，但能消掉 4 个 P0。应最先做。
2. **S1-3（项目隔离）是唯一"重"的**：要么加 `project_id`（123 个迁移之后的又一次大迁移 + 回填），要么逐接口 join `ProjectClusterNS`（易漏）。建议先给 `alerts/tickets/approvals` 三张最痛的表加列（折中方案），其余走 join。
3. **第二阶段不要先做流水线美化**：`release.py` 已经有 21 条路由，够用；真正的断点是 S2-1 仓库接入。没有它，AI 生成修复、代码扫描、版本定位全部是空中楼阁。

## 6. 结论（一句话版）

**第一阶段不是"缺功能"，是"缺边界"**——把 8 条平行执行入口收成 1 条、把 4 个裸端口关掉、把 1 把密钥拆成 3 把、把 25 个审计点补到 285 个，平台的"可交付"程度会跳一个台阶，且几乎不需要新写业务逻辑。
**第二、三阶段才是"缺功能"**——仓库接入是总开关，没有它，后面 12 项都挂不上。
