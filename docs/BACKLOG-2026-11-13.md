## 一、存储与数据量（**暂缓**，等真到瓶颈再动）

### 实测现状（2026-11-13，库 `autohealops` 3.4GB）

| 表 | 行数 | 数据 MB | 索引 MB |
|---|---|---|---|
| resource_snapshots | 7,161,718 | 953.3 | **1585.2** |
| pod_metrics_5m | 762,348 | 89.1 | 173.4 |
| pod_metrics | 784,082 | 82.2 | 253.5 |
| db_metric_snapshots | 980,656 | 81.6 | 126.9 |
| k8s_events | 34,407 | 14.3 | 10.8 |

两个信号：① `resource_snapshots` **索引比数据大 1.6 倍**；② Pod 指标在 MySQL 与 Prometheus **各存一份**。

### 先要澄清的结论
「进集群慢」**不是数据库问题**——是前端实时调 K8s 接口（`misc-resources`、`nodes`）。已修复（355ms 级）。所以存储优化是**为将来增长**，不是为了修慢。

### 优化项（按性价比，全部待开发）

| # | 需求 | 说明 | 预估 |
|---|---|---|---|
| S1 | 索引瘦身 | 查未使用索引、按查询列序重建（历史案例：`db_metric_snapshots` 顺序对齐后 1.22s→0.10s） | 0.5d |
| S2 | 去掉重复存储 | 历史趋势查 Prometheus，MySQL 只留「告警时刻快照」+ 事件级数据 | 2~3d |
| S3 | 分区 + 保留策略 | 按天分区；原始留 7~14 天，长期只留 5m/1h 降采样 | 1d |
| S4 | MySQL 换 SSD | 现 HDD（rotational=1，7G RAM/4 核）是最大短板，比换引擎见效快 | 运维，0 代码 |
| S5 | 时序外迁 | VictoriaMetrics（单机轻、压缩 10~20x）或 ClickHouse；关系数据留 MySQL | 1~2 周 |

**触发阈值**（到这才值得做 S5）：单表 > 5000 万行 / 库 > 50GB / 常态慢查询 > 100ms。
**不做**：把业务数据塞 etcd（KubeSphere 那套不适用，etcd 对写入频率敏感、建议单库 <8GB）。

### 6.6 SQL 终端能力清单（2026-11-13 17:35 老板追加）

> 定位：不是"简单查询框"，要做成**数据库客户端**（Navicat / DBeaver 那种），同时受平台权限与审批约束。

| 分类 | 能力 | 说明 |
|---|---|---|
| 视图 | **列表视图** | 数据库管理页保留「树视图 / 列表视图」切换，列表用于批量与分组管理 |
| 对象浏览 | 表 / 视图 / **函数** / **事件** / 存储过程 / 触发器 | 左侧资源树展开到对象级；点表自动 `SELECT * FROM t LIMIT 100` |
| 库管理 | **创建库 / 删除库 / 编辑库** | 编辑 = 字符集 / 排序规则 / 备注；删除需二次确认 + 审批（见 6.7） |
| 表结构 | 查看 / **改结构** | **不限范围**（加列/删列/改类型/改默认值/加删索引/改表名均可），执行前出 DDL 预览 + 二次确认 / 审批 |

### 6.7 数据库审核机制（2026-11-13 17:45 老板定稿为「简化版」）

**核心口径**
- **按实例配置**是否审核：不同数据库实例可以分别设置「查询是否要审核」「写入/更新是否要审核」「DDL 是否要审核」「导出下载是否要审核」
- **审批人 = 项目管理员**（该实例所属项目/集群的管理员；平台侧 admin 兜底）
- 全量留痕：`db_operation_audits`

**流程（简单直接）**

```
普通用户输入 SQL → 点「执行」
        │
        ├─ 该实例该动作「无需审核」 → 二次确认 → 直接执行
        │
        └─ 「需要审核」 → 弹窗显示将执行的 SQL 全文 + 目标实例/库
                          → 点「提交审核」
                                │
                     项目管理员收到审核单（站内通知/审批列表）
                                │
                        ┌───────┴────────┐
                     同意              拒绝（填理由）
                        │                └→ 申请人看到拒绝原因，可改 SQL 重新申请
                        ▼
              申请人可以「立即执行」或「指定一个时间执行」
                        │
              （单次有效，执行后审批单置 executed；指定时间到点自动执行）
```

**要点**
| 项 | 规则 |
|---|---|
| 审批单内容 | 实例、库、SQL 全文、动作类型、申请人、提交时间、状态 |
| 审批人 | **项目管理员**（已确认 2026-11-13 17:48；该实例所属项目的管理员，可多人，任一同意即通过） |
| 通过后 | 申请人二选一：**立即执行** / **指定时间执行**（定时到点自动执行） |
| 有效性 | 单次有效；执行完置 `executed`；超时未执行置 `expired`，需重新申请 |
| 下载类 | 审批通过发**一次性下载链接**，用一次失效（含备份产物下载）；下次再下载需重新审批 |
| 查询审核 | **可以按实例打开**（生产库 SELECT 也审） |
| 写操作 | 平台内仍保留二次确认（不硬拦），与审批串联：先确认 → 再审批 |

**状态机**：`pending → approved → executed | expired`；`pending → rejected`

**与现有机制复用**
- 审批单走现有 `approvals` / `approval_flows`
- 通知走现有通知渠道 + 站内消息
- 只读查询走 `readonly_username`（字段已存在）

### B20（2026-11-15 新增）agent 接入库的「库管理 / 原始 SQL 导入 / 整库备份 / 导出 mode」能力补齐

**现状（核实过的）**：agent 侧 method 只有 `DbHealth` / `DbObjectDDL` / `DbExport` / `DbImport` / `DbSchemaByKey` / `QueryDatabaseByKey`。
平台新增的这几项能力对 agent 库返回 400「该操作暂不支持 agent 接入的库」：

| 能力 | agent 现状 | 缺口 |
|---|---|---|
| 建库 / 删库 | 无 method | 需新增 `CreateDatabase` / `DropDatabase` |
| 原始 SQL 导入（stop/skip 两种错误模式，不限大小） | 只有 `DbImport`（按表/对象语义，非原始 SQL 流） | 需新增 `ImportSqlRaw`（流式分批 + 错误模式） |
| 整库备份（仅下载不落盘） | 无 method | 需新增 `Backup`（mysqldump 语义，流式回传） |
| 导出 `mode=structure|data|both` | `DbExport` 不认 mode（恒 both） | 需扩展 `DbExport` 入参并灰度 |

**为什么**：这些是 2026-11-15 平台侧新增的数据库运维能力，实现时只做了「直连库」（平台自己连），agent 侧方法没同步加。不是架构限制——agent 已有同类 DB 方法，可照现有 pattern 扩展。

**要做**：① executor/agent 侧新增 4 个 method（协议用现有 mTLS 帧，method 名字 + payload/响应结构定稿）；② api-server `db_connections.py` 去掉这 4 处的 400 分支，改走 agent_gateway；③ agent 版本升级 + 灰度（现网 0.2.16）；④ 兼容：旧 agent 收到新 method 要返回明确「版本过低」而不是超时。
**预估**：2~3 人日（含 agent 发版与灰度验证）。

## R41 三域 Agent 架构（K8s 应用 / 虚拟机应用 / 数据库，2026-11-17 讨论定稿）

> 老板：目前接了 K8s、虚拟机、数据库，后期把虚拟机里部署的应用也接进来 → 是否要三条 agent？
> **结论：不拆三个 agent，采用「一个 Agent Runtime + N 个 Domain Profile」。**

### R41.1 架构结论与理由

| 方案 | 复用 | 跨域故障 | 维护/评估 | 结论 |
|---|---|---|---|---|
| 三个独立 agent | 循环/工具协议/去重/轮数/结论格式/审批/审计全写三遍 | 要靠 agent 间通信 | ×3 | ❌ |
| **一个内核 + 三域 Profile** | 写一遍 | 一个循环内可横向调多域工具 | ×1 | ✅ |
| 多 agent 协作（orchestrator） | — | 域间协商 | 高 | 二期再评估 |

**现状已具备雏形**：`session.category` → domain 路由
```
{"db": "database", "node": "all", "cluster": "all"}  默认 "application"
tool_registry.list_tools(domain=_domain)
```
只需新增 `vm-app` 域 + 对应工具集，**不需要新写一个 agent**。

### R41.2 三个域的差异（要分别做的部分）

| 维度 | K8s 应用（现有） | 虚拟机应用（新增） | 数据库（现有） |
|---|---|---|---|
| 证据 | pod describe / events / 日志 / 指标 / JVM | **进程、端口、systemd 服务状态、应用日志、磁盘、JVM** | 慢 SQL、锁等待、连接池、执行计划 |
| 工具 | 现有 9 个（exec_in_pod/describe_pod/search_logs/get_pod_metrics/get_hpa/get_deployment/query_db_health/rag_search/jvm_diag） | **需新增 host-agent 工具**：proc_top / service_status / read_log / disk_usage / netstat / 远程 jvm_diag | query_db_health + 慢 SQL / 锁 / 连接池分析（可扩） |
| 处置矩阵 | 删 Pod、重启、扩容、回滚 | **重启服务、清理临时文件、扩容磁盘、回滚发布** | **只给方案**（红线），DDL 走审核 |
| 风险模型 | Pod 级，影响面小 | **服务级，可能影响整机 → 审批更严** | 极高，禁自动执行 |
| 知识库 | K8s/Java 故障 | VM/中间件/部署发布 | SQL/索引/锁 |

### R41.3 改动点清单

| # | 改动 | 落点 |
|---|---|---|
| A1 | 域枚举新增 `vm-app`（并明确 `k8s-app` 替代现 `application` 命名） | `api-server/app/services/agent_service.py`（domain 映射）、`tool_registry.py` |
| A2 | 工具按域可见：VM 域不暴露 k8s 工具，反之亦然 | `tool_registry.list_tools(domain=...)` |
| A3 | 系统提示词按域（现有 `SYSTEM_PROMPT` 是 K8s 专用） | `ai-service/app/services/agent_service.py` + `prompt_engine` 模板 |
| A4 | 知识库检索按域过滤（避免 VM 问题命中 K8s 文档） | `rag_service` + 知识库分类字段 |
| A5 | 处置矩阵按域（尤其 VM 服务级审批更严、DB 仅方案） | `plan_service` 风险分级 + 审批策略 |
| A6 | 跨域串联：会话允许一个循环内调多域工具（如 K8s 应用慢 → 查 DB） | 编排层 domain=all 的既有能力复用 |

### R41.4 虚拟机应用接入的前置工程（不在 agent 本身）

1. **host agent**：VM 侧常驻采集器（进程/端口/systemd/日志/磁盘/网络/JVM），上报同现有集群 agent 的模式；
2. **工具实现**：上述 6 个 VM 域只读工具（executor 侧新增，走 SSH/本地）；
3. **处置实现**：重启服务 / 清临时文件 / 扩容磁盘 / 回滚发布（全部走审批 + 审计）；
4. **资产模型**：VM 与「VM 上的应用」两级实体（服务名/端口/部署目录/关联 DB）。

### R41.5 验收

1. 同一会话可按 category 选中 vm-app 域，工具清单里不出现 k8s 工具。
2. K8s 应用诊断循环中可调用 database 域工具完成跨域关联。
3. VM 域处置动作全部产生审批单 + 审计，无法绕过。
4. 三域共用同一套 trace / 去重 / 轮数上限 / 结论格式。

## R42 Agent 运行轨迹（trace）可视化（2026-11-17 讨论定稿 · ✅ 2026-11-18 demo 定稿，需求见 `AGENT-TRACE-REQUIREMENTS-2026-11-18.md`）

> 目的：agent 开发工作台——**调试、复现、评估、审计**四件事都依赖 trace 可见。
> 好消息：后端数据已齐，`DiagnosisMessage` + `tool_steps` 就是完整 trace，主要缺前端渲染。

### R42.1 现有数据（可直接用）

| 数据 | 内容 |
|---|---|
| `DiagnosisMessage` | role（user/assistant/tool）、tool_name、tool_args、tool_output |
| `tool_steps`（编排层聚合） | step、tool、label、args、success、duplicate、output |

### R42.2 前端形态（落地 `frontend/src/pages/AgentChat.tsx`）

```
顶部：模型 · 步数 · 耗时 · token 统计
主体：步骤时间线
  ① decide  → 调 describe_pod             ✓ 0.8s  [展开原始输出]
  ② observe → 3 个事件：Readiness probe failed
  ③ decide  → 调 search_logs(previous)    ✓ 1.2s
  ④ observe → Full GC 停顿 4.2s × 3
  ⑤ decide  → 调 jvm_diag(heap_info)      ✓ 2.1s
  ⑥ final   → 根因卡片（root_cause / suggestions / handling_advice）
底部：重跑该会话 / 导出 trace(JSON)
```

要素要求：
- 每步**可展开**看原始入参与输出（不折叠掉证据）
- 失败步骤**标红**、重复调用**打标**、达到轮数上限**提示**（对应现有的 `MAX_CONSECUTIVE_DUP` / 上限逻辑）
- 结论单独成卡片，与步骤区分
- 三域（k8s/vm/db）共用同一套渲染

### R42.3 接口

- 优先复用现有会话消息接口；不足时新增 `GET /api/v1/diagnosis/sessions/{id}/trace`（返回 steps + 统计 + 结论）。

### R42.4 二期（agent 开发闭环）

- trace 沉淀为 **eval 数据集**：标注正确答案 → 跑批量回归 → 算诊断准确率 / 平均步数 / 工具命中率 → 支撑 prompt 与工具迭代。

### R42.5 验收

1. 任一诊断会话可看到完整步骤序列，展开能看到工具原始输出。
2. 失败/重复步骤有明确视觉标记。
3. 顶部统计（模型/步数/耗时/token）与实际一致。
4. 可导出 trace JSON 用于复盘与评估。

### H4 补充修复：回放出现「cdcd」重复（2026-11-18 14:36 老板反馈）

- 现象：录屏里执行 `cd`，回放时显示 `cdcd`。

### H4 补充修复：同一时间同一用户出现两条会话（一空一有内容）（2026-11-18 14:44）

```sql
-- 仅清理修复前的噪声会话（0 秒、无输入）
DELETE FROM host_sessions WHERE duration_sec <= 2 AND COALESCE(bytes_in,0) = 0;
```

### D3 会话录制（细化 · 2026-11-17 15:24 老板追加：**只在操作时录制**）

**录制触发与分段（核心机制）**

- **只在实际有操作时录**：以用户 **stdin 输入事件（按键 / 粘贴 / 回车）为录制锚点**；无任何输入的空闲时段**不产生录制内容**。
- 每一段录制 = 从一次输入开始 → 该操作引发的全部输出 → **输出静默超时结束**（默认 30s，可配）。
- 回放时按段拼成时间线，段与段之间用「空闲 N 分钟」占位（折叠展示，不是录像）。
- 不录制：平台后台采集、系统内部任务、无用户参与的自动化连接、纯空闲等待。

**边界情况**

| 场景 | 处理 |
|---|---|
| 用户执行 `tail -f` / 长任务输出 | 属该操作引发的输出 → **持续录到输出停止或用户下一次输入** |
| 用户只是挂着不动 | 不录（会话仍在，只是没有录像段） |
| 用户粘贴大段脚本 | 作为一次输入事件记录（含内容摘要，超长截断并标注长度） |
| 会话中短暂离开 | 超过静默阈值即结束当前段，回来再操作新开一段 |

**其它要求**

- 入口：节点管理 →「会话录制」列表（用户 / 主机 / 开始时间 / 总时长 / **操作段数** / 大小 / 回放）。
- 存储：本地磁盘起步，保留 90 天（后续按压力再迁对象存储）。
- 实施第一步：先核查现有 `host_terminal.py` / `host_sessions` 到底录了什么（实测无录像，可能是开关未开或只记了命令审计），再定「补录制」还是「修开关」。
- **已定（2026-11-17 15:25）**：输出**录到停止**（含 `tail -f` 这类持续输出，直到输出静默或用户下一次输入）；空闲静默阈值默认 **30s**（可配）。

### R55 容器日志「跟随 / 时间段下载」不支持 agent 接入集群（✅ 2026-11-19 代码已修，待 agent 升级生效）

- **现象**：agent 接入的集群（如测试环境 999025）查看容器日志时，跟随模式报
  `502 集群客户端不可用: client config 构建失败: invalid configuration: no configuration has been provided`。
- **根因**：`k8s-executor/internal/logstream/{server,watch}.go` 用**平台侧 kubeconfig 直连集群**；
  agent 接入集群在平台侧没有 kubeconfig → 构建 client config 失败 → 502。
- **受影响接口（2026-11-19 实测修正）**：仅 `GET /pods/{pod}/logs/download?start=&end=` 的**时间段下载分支**
  （走 `logstream_client.fetch_logs` → executor 日志流 9099）。
  实测复现：`502 日志流不可用，无法按时间段过滤：502 集群客户端不可用: client config 构建失败…`
- **不受影响（实测 200，与 KubeSphere 行为一致）**：
  ① 默认查看（`/workloads/{kind}/{name}/logs?tail=N`，取一段快照）；
  ② 跟随开关（`/logs/stream`，实现是**每 2s 轮询 tail 增量**，不是长连续流）；
  ③ 聚合日志 `since_seconds`/`all=true`（走 gRPC，经 agent 隧道）。
  → 即「点开看一段 + 打开开关才实时」本来就是现状设计；坏的是**时间段下载**这一条。
- **要求**：日志流与时间段下载按集群接入方式分流 —— agent 集群走 agent 隧道（与 tail 同源），
  平台集群继续走 executor logstream；并在前端对 502 做**降级**（自动回落 tail 模式并提示「跟随不可用」），
  不允许直接把 502 原文弹给用户。
- **影响面**：仅 agent 接入集群 + 跟随模式/时间段下载；平台直连集群不受影响。
- **实施（2026-11-19）**：`GetPodLogsRequest` 加 `timestamps`/`since_seconds` 字段（向后兼容）；
  Go `GetPodLogs` 透传 `PodLogOptions{Timestamps, SinceSeconds}`（`tail_lines=0 && timestamps` 取整份）；
  api-server 在 `resources.py` 按 `clusters.source` 分流（agent → gRPC 带时间戳 + 平台侧过滤；direct → 原 logstream）；
  旧 agent 不认新字段 → 明确 502「agent 版本过低，请升级」，不再静默空文件。
- **生效条件**：需升级集群内 agent 镜像（新字段由 agent 侧 executor 读取）；平台侧升级后旧 agent 仍只影响「整份/时间段下载」，tail 查看不受影响。
- **2026-11-19 追加实测**：agent 集群上 `all=true`（不带时间段）的聚合日志返回 **0 行且无报错**（静默空），
  前端「下载(gzip)」正是用 `all=true&tail=5000` → **下载得到的是空文件**；带时间段则返回 502 + 0 行。
  即：agent 集群的「按时间段下载」不仅有 502，还有「静默空文件」两种失败形态。
- **下载文件名与区间语义（待老板确认）**：现文件名用 `Date.now()`（下载时刻）拼接，
  与用户选择的开始/结束时间无关；建议改为 `{namespace}_{name}_{开始}_{结束}.log.gz`（本地时区），
  内容严格按所选区间过滤。若只选结束时间，则按「结束时间往前 N 分钟」口径实现。

#### 走隧道后的流量影响（2026-11-19 评估）

- **方向**：agent 主动连平台（push 反向隧道），日志字节 = **集群出站流量**（agent → 平台）。
- **量级估算**（按 200~300 B/行）：
  | 场景 | 单次/单连接 | 说明 |
  |---|---|---|
  | tail 5000 行 | 约 1~1.5 MB | 一次性 |
  | 跟随（10~50 行/秒） | 2~15 KB/s ≈ 16~120 kbps | 仅用户打开时 |
  | 并发 3~5 路跟随 | 数十 KB/s ~ 1 Mbps 级 | 正常运维规模 |
  | 时间段下载（整份日志） | 几十 MB ~ 数百 MB | **最伤流量**，压缩后约 1/5~1/10 |
- **对比基准**：agent 指标上报约 810 条/10s（≈8 KB/s 级），日志跟随峰值约为其几十倍，但只在有人查看时发生。
- **实施口径（写进 R55）**：
  1. 隧道只承载 **tail + 跟随**，**禁止 all_lines 全量下载走隧道**（大文件下载另走集群内生成 + 分片拉取，或提示走运维通道）；
  2. 过滤下推到集群侧（keyword/since 在 agent 内过滤，只回匹配行），避免全量过网；
  3. 每集群并发跟随连接上限（建议 ≤5）+ 单连接速率上限；
  4. 隧道是单条 gRPC 多路复用，日志流与指标上报共用 → 需要优先级/限流，避免把指标上报堵住；
  5. 下载默认 gzip（已有），SSE 跟随可评估 deflate；
  6. 隧道字节数纳入监控（按集群统计上下行）。

### R59 Agent 版本管理与升级通道（2026-11-20 老板定，未开发）

> 来源：R57 联调发现 —— agent 接入集群（999025）调用新 gRPC 方法报
> `unknown method ListHPA for service executor.ExecutorService`，平台侧能力已就绪但集群内 agent 二进制是旧版。
> 同类问题已出现两次（R55 日志下载、R57 HPA），属结构性问题，不是单次疏漏。

**现状（2026-11-20 核实）**
- 平台通过反向隧道把 gRPC 调用转发给集群内 agent，agent 侧跑的是**独立打包的 executor 二进制**，版本与平台侧解耦。
- 平台侧没有任何「agent 版本」的概念：不知道各集群 agent 是哪个版本、不支持的能力有哪些、也无法远程升级。
- 表现：新功能对直连集群立即可用，对 agent 集群静默失败或报 `unknown method`，只能靠人工逐个排。

**需求**
1. **版本上报**：agent 启动时经隧道上报自身版本（git commit / 构建号 + 能力列表），平台持久化到集群表并展示在「集群管理 → 集群详情」。
2. **能力协商**：平台调用前判断 agent 是否支持该能力，不支持时返回明确文案（如「该集群 agent 版本过低，不支持 HPA 管理，请升级到 vX」），**不允许把 `unknown method` 原文抛给用户**。
3. **版本可见性**：集群列表加「agent 版本」列 + 「需升级」标记（低于平台要求的最低版本时高亮）。
4. **升级通道**：平台侧触发滚动升级 agent（拉起新版本 DaemonSet/Deployment 或下发升级指令）；至少提供「一键生成升级命令/YAML」供运维执行。
5. **兼容性口径**：proto 只做向后兼容变更（只加字段/加方法，不删不改语义），旧 agent 遇到新方法返回可识别的 `Unimplemented`，平台侧统一转成友好提示。

**验收**
1. agent 集群详情能看到版本号与能力列表；平台侧最低版本不满足时列表有「需升级」标记。
2. 对旧版 agent 调用 HPA 接口，前端提示「agent 版本过低，请升级」而不是 `unknown method`。
3. 升级 agent 后（至少测试环境 999025）HPA 管理、日志时间段下载（R55）均恢复正常。
4. 能对指定集群触发一次升级并验证成功（或产出可执行的升级清单）。

**工时**：~2.5d（版本上报+能力协商 1d / 前端展示 0.5d / 升级通道 1d）。

**依赖**：agent 打包发布流程（镜像构建 + 版本号注入）需确认现状。
