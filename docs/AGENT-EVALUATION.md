# Agent 化改造评估：现状 vs 目标

> 状态：**评估文档**（2026-08-26 老板讨论产出）
> 定位：回答「Pod 报警自愈 / 应用诊断 / 数据库诊断 算不算 agent、离 agent 差多远、要不要改、怎么改」
> 关联：`ARCHITECTURE.md`（三服务架构）、`AGENT-DIAGNOSIS.md`（应用诊断助手方案）、`DIAGNOSIS-CENTER.md`（诊断中心方案）

---

## 1. 结论摘要

**核心定位（老板 2026-08-26 拍板）：**

- Pod 报警自愈 → **唯一能做成 Agent 的能力**（资源/编排层，平台能自动执行 → 诊断 + 判断 + 自愈 + 审核闭环）
- 应用诊断助手 → **诊断能力，做不了 agent**（只能出结论 + 建议，改代码走发布，平台不执行）
- 数据库诊断 → **诊断能力，做不了 agent**（只能出方案，DBA 执行，平台不碰数据）

应用诊断 / 数据库诊断本质是「**诊断工具**」：作为 Agent 的数据来源/工具 + 独立用户入口，不做自动执行闭环。

**Agent 化的本质**：从「流程调用 AI」变成「AI 编排流程」——把"下一步做什么"的决策权从代码交给模型，同时用护栏（白名单/审批/审计）锁住风险边界。

**执行铁律（老板 2026-08-26 补充）**：诊断结果 ≠ 直接执行。按根因所在层决定执行域——资源层问题平台可自愈；**代码/配置层问题必须走发布流程，不直接改容器**；数据库层只给方案；基础设施层转工单（详见第 5 节执行决策矩阵）。

**诊断铁律（老板 2026-08-26 补充）**：诊断 = 只读探查。**可以进入容器/数据库查看信息，但禁止增改删**——容器内只读命令（exec 白名单）、数据库只读账号；诊断永远不改任何东西。增改删只能发生在：① Pod 编排层自愈（agent 白名单 + 审批）② 人工（改代码走发布 / DBA 执行）。

**推荐路径**：不要追求全自主 agent，采用**「确定性外壳 + 智能内核」混合形态**——确定性的活（采集/重启/审批路由/通知）留在代码，不确定性的活（诊断/方案/路径选择）交给 agent。这是运维领域当前最稳的形态。

## 2. 现状回顾

### 2.1 架构（三服务 + 前端）

| 组件 | 职责 |
|---|---|
| api-server (FastAPI) | 编排中枢：告警闭环、自愈策略、审批流、通知路由、知识库、会话 API |
| k8s-executor (Go) | K8s 资源操作 + 指标/事件采集（watcher）+ gRPC 服务（Pod 操作/ExecInPod/QueryPrometheus） |
| ai-service (FastAPI) | AI 大脑：告警诊断、方案生成、RAG 知识库、数据库诊断分析（/db-diagnose） |
| frontend (React+AntD) | 控制台：告警/自愈/审批/诊断中心/知识库/监控 |

共享 MySQL + Redis，executor 通过 gRPC 被 api-server 调用。

### 2.2 三大功能

**① Pod 报警自愈**
- 触发：executor watcher 发现异常（CrashLoopBackOff/OOMKilled 等）→ 生成 Alert
- 流程：Alert → AI 诊断（ai-service）→ 生成修复方案（模板/知识库填充）→ 按自愈策略（时间段 auto_heal/manual）→ 自动执行 或 审批 → 通知项目群
- 决策点：时段策略（代码）、命令白名单（代码）、审批路由（代码）——AI 只产方案

**② 应用诊断（AI 诊断助手）**
- 触发：用户在会话里发起（选集群/ns/pod + 描述问题）
- 流程：AI 规划 → 调工具（ExecInPod 只读命令 / ES 日志 / describe / 指标）→ 多轮追问 → 输出诊断结论 + 处理意见 → 确认后落盘知识库
- 决策点：下一步查什么（AI 自主）——**已有 agent 雏形**

**③ 数据库诊断**
- 触发：用户在诊断中心点「诊断」
- 流程：DBConnection 只读账号 → db_collector 采集（连接数/锁等待/表空间/慢 SQL）→ 落趋势表 → ai-service /db-diagnose 分析 → DiagnosticReport → 沉淀知识库（只给方案，不执行修改）
- 决策点：无（输入输出固定），AI 是纯分析引擎

## 3. Agent 判定标准（五要素）

一个系统算不算 agent，看五条：

| 要素 | 含义 | 现状三大功能 |
|---|---|---|
| ① 自主目标循环 | 感知 → 规划 → 行动 → 观察 → 调整，直到目标完成 | ❌ 循环在代码里（定时器/按钮/消息），不在模型里 |
| ② 工具调用自主性 | AI 自己决定"下一步查什么/做什么" | ⚠️ 仅应用诊断助手有 |
| ③ 记忆与上下文 | 跨轮次、跨任务的上下文保持与复用 | ⚠️ 会话级有，任务级没有 |
| ④ 目标导向终止 | 自己判断"问题是否解决"来结束 | ❌ 终止条件都是代码定的（超时/恢复/审批） |
| ⑤ 跨域协作 | 一个智能体同时调度多个能力域 | ❌ 三个功能三个入口，互不感知 |

**判定**：三者现状都是「被编排的 AI 环节」，不是自主智能体。但**只有报警自愈具备 agent 化前提**（能自动执行）；应用诊断、数据库诊断因「只能诊断、不能执行」，本质定位就是诊断工具，不做 agent。

## 4. 三大功能逐项对照

| 维度 | ① 报警自愈 | ② 应用诊断 | ③ 数据库诊断 |
|---|---|---|---|
| 触发 | 事件（watcher） | 用户会话 | 用户按钮 |
| 流程编排者 | 代码（alert_auto_service） | AI（工具循环） | 代码（db_diagnosis_service） |
| AI 角色 | 诊断 + 方案生成 | 诊断 + 对话 | 分析报告 |
| 工具调用 | 无（AI 不直接调工具） | 有（ExecInPod/ES/describe） | 无（采集是代码干的） |
| 多轮上下文 | 无（单次） | 有（会话级） | 无（单次） |
| 执行能力 | 有（重启/update，受策略约束） | 无（只诊断，人工处理） | 无（只给方案） |
| 知识库复用 | 有（方案模板/占位符） | 有（闭环落盘） | 有（db_ 前缀沉淀） |
| 能否 agent 化 | ✅ 能（可自动执行） | ❌ 不能（只诊断） | ❌ 不能（只诊断） |
| 定位 | 自愈闭环（唯一 agent） | 诊断工具 | 诊断工具 |

## 5. 执行决策矩阵（场景化）——老板 2026-08-26 补充

> 核心原则：**诊断结果 ≠ 直接执行**。先判断根因所在层，再决定执行域/执行主体/决策模式。
> 典型例子：Pod 内应用报错若根因是代码问题，**必须走发布流程（重新构建镜像+发布），不是直接改容器**——容器层操作解决不了代码问题。

### 5.1 执行域分层（修复动作归属哪一层）

| 执行域 | 修复动作示例 | 执行主体 | 决策模式 |
|---|---|---|---|
| A. 资源/编排层 | 重启 Pod、删异常 Pod、update 资源、改 limit、补 secrets、扩缩容 | k8s-executor（平台） | 自愈自动执行 / 审批（按风险分+时段策略） |
| B. 应用代码/配置层 | 改代码、改配置、升级镜像版本 | **发布系统（CI/CD）或开发** | 平台不碰容器，转**发布建议**：定位改动点→触发发布/通知开发 |
| C. 数据库层 | 加索引、改 SQL、kill 会话、调参数、改数据 | DBA / 人工（平台只读） | 只给方案 + 落知识库，绝不直接改 |
| D. 基础设施层 | 加节点、扩容存储、网络调整 | 运维 / 工单 | 生成工单 / 通知值班 |

### 5.2 场景 → 决策示例

| 诊断结论（示例） | 根因层 | 执行决策 |
|---|---|---|
| Pod OOMKilled（内存超 limit） | A 资源层 | 自愈：重启 / 小幅调 limit（按策略自动或审批，以风险分为准）；若反复 OOM → 怀疑代码内存泄漏，**升级到 B 层转开发** |
| CrashLoopBackOff（日志显示配置错误） | B 配置/代码层 | **不改容器**！建议改配置 → 走发布流程 / 人工 |
| 镜像拉取失败（认证/镜像名错） | A 资源层 | 白名单内（补 secrets/改 image）→ 自愈；否则审批 |
| 应用 500 / 业务报错（代码 bug） | B 代码层 | 平台不修代码 → 发布建议（定位服务/版本，触发发布或通知开发） |
| 慢 SQL（全表扫描 19.6s） | C 数据层 | 只给方案（加索引/改 SQL），DBA 执行 |
| MySQL 连接数爆满 | C 数据层（运行态） | 临时缓解（kill 空闲会话）仍需 DBA；根治方案人工 |
| 节点 NotReady / 磁盘满 | D 基础设施层 | 工单 / 值班通知，人工处理 |

### 5.3 决策输入与输出

- **输入**：故障类型 + 根因所在层 + 修复动作类型 + 风险分（对接 `DECISION-BOUNDARY.md`）+ 时段策略（工作日/非工作）
- **输出**（五选一）：
  1. **自愈执行**——A 层且白名单内
  2. **审批执行**——A 层但高危（**大幅改 limit**/删服务/跨命名空间等，以风险分为准）
  3. **发布建议**——B 层，触发发布或转开发
  4. **只给方案**——C 层，落知识库待人工
  5. **工单/值班**——D 层

> 注：B 层闭环需要平台对接**发布系统**（Jenkins/ArgoCD/内部发布平台），当前项目无此能力，列为后续可选建设（见阶段 1 改造）。

### 5.4 自动化边界（什么能全自动，什么必须人工）——老板 2026-08-26 确认

> 原则：**不需要人工参与的 → 做成 agent 全自动闭环；需要人工判断的 → 转审核/人工。**

**全自动（agent 直接闭环）需同时满足全部条件：**

1. 根因层 = **A（资源/编排层）**
2. 修复动作在**白名单**内（重启/update/补 secrets/**小幅常规调整**等幂等可回滚操作；改 limit 视幅度与风险分：小幅可自动，大幅走审批）
3. **风险分低于阈值**（对接 `DECISION-BOUNDARY.md` 风险评分；改 limit/删服务等高危操作不在内）
4. **时段策略允许**（当前处于 auto_heal 时段）
5. 该资源**无反复自愈失败记录**（对接 `ALERT-SUPPRESSION.md` 循环抑制，避免治标不治本）

**任一条件不满足 → 升级人工：**

| 不满足条件 | 升级路径 |
|---|---|
| 根因在 B/C/D 层 | 发布建议 / 只给方案 / 工单值班 |
| 动作不在白名单或高危 | 审批流（值班/管理员） |
| 风险分超阈值 | 审批流 + 升级链 |
| 非 auto_heal 时段 | 全部走审批（现有策略） |
| 反复自愈失败 | 停止自动，转 AI 深度诊断 + 人工介入 |

> 即：**agent 自动化的边界 = 条件 1-5 全真**；边界外一律留给审核/人工。模型只能建议，无权自行扩大自动化边界。

### 5.5 边界的定义与演进机制（三层 + 默认拒绝 + 闭环）——老板 2026-08-26 确认

> 问题：工作场景不断新增，自动化边界不能靠一次性列清单定死。
> 原则：**边界是活的**——红线不可动，策略可配置，AI 只能建议，默认拒绝，人工每次处理都是边界养料。

**三层结构：**

| 层 | 内容 | 谁控制 | 可变更性 |
|---|---|---|---|
| ① 红线层（安全底线） | 改数据库、删服务、改代码、跨集群/批量操作 | 代码写死，无配置入口 | **永不自动** |
| ② 策略层（规则库） | 白名单、风险阈值、时段、场景规则（故障类型×资源×动作→决策） | 管理员在平台配置（DB + 管理界面） | 可配置，新增场景=新增规则，不改代码 |
| ③ 学习层（AI 建议） | 从人工处理案例中沉淀"可自动化"建议 | AI 提出，**人工确认后生效** | AI 无权自行扩大边界 |

**兜底原则：默认拒绝。** 任何场景匹配不到规则 → 走人工审批，宁严勿松。

**新场景演进闭环：**

```
新场景 → 默认人工处理 → 复盘沉淀 → AI 建议规则
       → 影子模式试跑（只记录不执行，观察 N 次）
       → 人工确认启用 → 成为正式规则（②策略层）
```

**配套要求：**

- 规则变更全留痕、可回滚（审计）
- 新规则必须先跑**影子模式**（记录"如果当时自动会怎样"，不实际执行），验证无副作用再启用
- 规则匹配按优先级：具体场景规则 > 通用规则 > 兜底人工
- 每次人工处理都是一次规则学习样本（打标：当时为什么转人工）

## 6. 差距总结

1. **决策权位置**：现在"走哪条路"由代码/配置决定；agent 化后**诊断路径**由模型决定（AI 判断先查日志、查指标还是查 DB），但**执行路径仍由矩阵/规则决定**（第 5 节）——模型只能在边界内自主
2. **上下文割裂**：三个功能各自为战——告警自愈不知道数据库诊断刚发现的慢 SQL，诊断助手不知道昨晚的自愈记录。agent 化后共享"任务记忆"
3. **工具未对 AI 开放**：executor 的 gRPC 能力（Pod 操作/ExecInPod/Prometheus）目前只有应用诊断助手在用；报警自愈和 DB 诊断的 AI 都"看不见工具"，只能拿到代码喂给它的数据
4. **无失败重试循环**：AI 诊断结果不好时，没有"换一种方式再查"的机制（应用诊断助手除外）
5. **安全护栏是硬编码**：白名单/审批/审计都在代码层，agent 化后需要变成"模型的硬约束"（防 prompt 注入、防越权调用）

## 7. 改造方案（三期）

> 核心：**Agent 化只针对报警自愈**。应用诊断、数据库诊断保持「诊断能力」定位，作为 Agent 的工具/数据源。

### 阶段 0：诊断能力工具化（打地基）

- 把现有诊断能力封装成**统一工具注册表**：executor gRPC（Pod 操作/ExecInPod/QueryPrometheus）+ ES 日志 + DB 采集 + 知识库 RAG
- 应用诊断助手、数据库诊断中心作为「诊断能力」保留独立入口，复用工具注册表
- 收益：Agent 和诊断助手共用一套工具；新增工具=注册一条定义
- 成本：api-server 加工具注册表 + 参数校验，executor 无需改动

### 阶段 1：报警自愈 Agent 化（核心，唯一 agent）

- 报警自愈引入 **agent 循环**（thought → tool call → observe → 继续/结束）：告警 → 诊断 → 调工具（含应用诊断/DB 诊断能力）→ 判断根因层 → 执行决策
- **执行决策矩阵落地**（对接第 5 节）：根因分层 A/B/C/D → 执行域路由 + 自动化边界判定（5 条件全真才自动）
- **应用诊断 / 数据库诊断作为 Agent 的工具**：根因在 B（应用）层时调应用诊断出建议→转发布；根因在 C（数据库）层时调数据库诊断出方案→转 DBA。**它们不自动执行，只产出结论/方案**
- **规则引擎 + 影子模式**：自动化边界可配置、可演进（第 5.5 节）
- **任务记忆**：同资源历次诊断/自愈/审批记录注入上下文
- **循环抑制**：反复自愈失败 → 停自动转人工
- 安全：工具调用统一走「白名单 + 参数校验 + 审计」，模型只产出意图，执行由代码把关
- 收益：AI 从「分析引擎」变「诊断+判断执行者」，闭环质量明显提升

### 阶段 2：全自主编排（可选，谨慎）

- 报警自愈的「路径选择」进一步交给 agent：告警 → agent 自主决定（诊断 → 查日志 → 查 DB → 自愈 → 升级审批 → 通知）
- 引入**风险评分作为 agent 的硬约束**（对接 DECISION-BOUNDARY.md）：低风险自动、高风险强制审批，模型无权绕过
- 引入**跨告警学习**：重复故障自动关联历史方案
- 风险：可预期性下降、prompt 注入面扩大，需更强护栏与灰度

---

## 8. 推荐路径

**阶段 0 + 阶段 1，暂不上阶段 2。**

理由：
- 运维场景**确定性优先**——告警闭环是要 7×24 稳定跑的，全自主 agent 的不可预期性是负债
- 阶段 1 的「报警自愈 agent 化 + 诊断能力工具化」兼顾了 AI 能力和流程确定性，且与现有自愈策略/审批体系天然兼容
- 阶段 2 可以等阶段 1 跑稳、积累了足够的真实诊断数据后再评估

一句话原则：**让 AI 决定"查什么、怎么查、怎么建议"，让代码决定"能不能执行、谁来批、发给谁"。**
