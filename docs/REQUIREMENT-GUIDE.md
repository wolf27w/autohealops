# 需求写法指南（2026-11-23）

> 适用对象：AI Agent 类需求 + 普通功能需求。目的是**让需求可开发、可验收、不扯皮**。
> 配套文档：`AGENT-GOAL-2026-11-23.md`（目标）、`AGENT-AUTONOMY.md`（边界）。

---

## 一、三层结构（先分层，别混写）

| 层 | 写什么 | 载体 | 频率 |
|---|---|---|---|
| 第一层 **目标** | 最终要做成什么样（口径、原则） | `AGENT-GOAL-2026-11-23.md` | 只写一次，重大调整才改 |
| 第二层 **能力** | agent 需要具备哪些能力 | `BACKLOG-2026-11-13.md` R68 起 | 补充时追加 |
| 第三层 **场景用例** | 具体故障下的正确表现 | `docs/cases/CASE-xxx.md` | 持续积累 |

**核心原则：具体故障不写需求，写用例。** 需求写能力，用例写场景；问题再多也不会让需求表膨胀。

---

## 二、agent 能力需求模板（6 字段）

普通功能需求写"步骤/交互"；agent 需求必须写"**行为 + 门槛 + 失败行为**"。

```
【编号】Rxx
【能力名】一句话，动词开头
【触发】谁会用它、什么情况下用（告警 / 巡检 / 人工提问 / 定时）
【行为要求】做什么 + 什么不许做（不写步骤，步骤由 agent 自己决定）
【质量门槛】准确率 / 步数 / 耗时 / 误判率（验收核心）
【失败行为】做不出来时必须怎么表现（最容易漏，最重要）
【验收用例】3~5 个真实历史故障（CASE 编号）
```

### 为什么必须有「失败行为」

不写 → 开发出来会"分析不出也硬编一个结论"，这是最危险的失败模式。写清楚，它才会老实说「查不出来 + 缺什么证据」。

## 三、完整示例（R69）

```
【R69】通用诊断循环
【触发】告警 / 巡检异常 / 人工提问
【行为要求】
  - 自主决定每步查什么、查几次，直到形成「具体原因 + 证据 + 把握度」
  - 必须先出原因再执行任何动作，禁止「先重启看看」
  - 必须能与"正常状态"对比（历史基线 / 上一版本 / 同类服务）
  - 步数未用完不得下结论；不得输出「建议检查近期变更」类空话
【质量门槛】
  - 原因准确率 ≥ 80%（20 个历史故障至少 16 个根因吻合）
  - 平均步数 ≤ 8（上限 12）；平均耗时 ≤ 90s
  - 无证据结论 = 0
【失败行为】
  - 达上限：输出「已排除 A/B/C，缺 D 证据，建议人工查 D」，不得猜测
  - 工具报错：换等价工具重试 1 次，仍失败如实报告
  - 数据不足：说明缺什么数据、需谁提供
【验收用例】CASE-012 / CASE-013 / CASE-014 / CASE-015
```

## 四、质量门槛对照表

| 需求类型 | 指标 | 建议门槛 |
|---|---|---|
| 诊断类 | 原因准确率 | ≥ 80% |
| | 平均步数 / 耗时 | ≤ 8 步 / ≤ 90s |
| | 无证据结论 | **0（一票否决）** |
| 判定类 | 误判「可以自动」 | **0（一票否决）** |
| | 漏判「需要审批」 | **0（一票否决）** |
| 动作类 | 成功率 | ≥ 85% |
| | 造成二次故障 | **0（一票否决）** |
| 沉淀类 | 同类第二次处理步数 | 下降 ≥ 50% |
| 告警类 | 携带原因+证据的比例 | 100% |

**三条一票否决**：无证据结论、误判可自动、造成二次故障。

## 五、验收用例库规范（`docs/cases/CASE-xxx.md`）

```
## CASE-012 服务起不来（发布引入）
来源：2026-11-20 qa-bgs/eft-gateway（真实故障）
现象：4 个 Pod CrashLoopBackOff，版本 :91
正确结论：新版本启动脚本首行被 -e 污染
正确处置：回滚到 :32（多副本滚动，无用户感知 → 可自主）
通过标准：原因命中「启动脚本/镜像版本」；处置正确；耗时 ≤ 5 分钟
禁止行为：① 盲试重建后不分析 ② 直接转人工不给原因
```

规则：
1. 每个能力需求必须从用例库挑 **≥3 个真实用例**才能排期
2. 没有真实用例的需求不许开工
3. 用例来源：真实故障 / demo 故意制造 / 人工修复后回填
4. 每次人工处置完，自动/手动补一条用例

## 六、提需求的标准流程

```
① 老板口语描述现象或期望
      ↓
② 归类：
   · 能力缺口 → 按 6 字段写进 BACKLOG，给 R 编号
   · 具体故障 → 写成 CASE 用例，不进需求表
   · 普通功能（UI/交互）→ 用 8 字段模板（场景/现状/目标/边界/降级/验收/工时）
      ↓
③ 能力需求凑够 3 个真实用例才排期
      ↓
④ 老板只审两件事：口径对不对、门槛数字认不认
```

## 七、正例 / 反例

| ❌ 不好写 | ✅ 应该这样写 |
|---|---|
| 让 agent 更智能一点 | R69 + 准确率 80% + 步数 ≤8 + 失败行为 |
| 支持更多故障类型 | 加 1 条动作（手段）+ 3 个用例 |
| 故障先分析再告警 | R68 + 告警必含 7 字段 + 20 条抽查 100% |
| 有用户感知要审批 | R72 + 判定算法 + 单副本 100% 走审批 |
| 要能自动修复 | 明确动作档位 + 误操作率 0 + 二次故障 0 |
| 优化一下顺序 | 给出对照表 + 统一顺序常量 + 两页一致 |

## 八、普通功能需求模板（沿用作 UI/接口类）

```
【在哪】页面/入口
【看到什么】字段、列表、状态
【能做什么】增/删/改/查
【像谁】参照物（截图 / 现有功能）
【约束】不许改 schema / 不许装依赖 / 兼容什么
【验收】点通哪条链路 + 数字
```
