# Agent 目标与处置流程（2026-11-23 老板定稿）

> 本文是**总纲**：定义 agent 要做成什么样。具体边界见 `AGENT-AUTONOMY.md`，需求编号见 `BACKLOG-2026-11-13.md` R68~R73。

---

## 一、目标（一句话）

> 让平台自己完成「发现故障 → 分析原因 → 判断能否自己解决 → 处置 → 验证 → 归纳」，只在**解决不了**或**会影响用户**时才需要人。

---

## 二、五条硬性口径（老板 2026-11-23 定，不放宽）

| # | 口径 | 含义 |
|---|---|---|
| 1 | **先分析，再告警** | 告警必须携带分析结论，不允许只甩「服务挂了」 |
| 2 | **能自己解决就自己解决** | 不是「转人工为默认」，转人工是兜底 |
| 3 | **必须给出具体原因** | 禁止「试一下重启看看」式盲试；先定位原因，再决定动作 |
| 4 | **生产有用户感知 → 人工确认** | 判据见第五节，可计算 |
| 5 | **生产无用户感知 → 不需审核** | 由 agent 自主执行，事后报备 |

补充原则：
- 分析不出原因 ≠ 可以乱试。分析失败就**如实说明"查不出来 + 已排除什么"**，转人工，不猜着修。
- 同一服务 10 分钟内只自动处置 1 次；修完没好转立即停手转人工，禁止连续试错。

---

## 三、完整处置流程

```
① 发现故障（告警源 / 巡检 / 人工提问）
       ↓
② 【强制】分析原因
   采集现场（日志/事件/指标/配置/最近变更）→ 对比正常态 → 形成假设 → 逐条验证
   硬要求：必须输出「具体原因 + 证据 + 把握度」
   分析不出 → 输出「已排除项 + 缺失证据」，直接转人工
       ↓
③ 发告警（携带 ② 的结论）      ← 紧急故障可先发「正在分析」再补发结论
       ↓
④ 判断能否自己解决（三问任缺一即转人工）
   a. 有没有对应手段？（动作库里有没有匹配动作）
   b. 生产环境是否有用户感知？（第六节）
   c. 把握度是否 ≥ 阈值？（默认 0.6~0.8）
       ↓                                   ↓
   全部满足                              任一不满足
       ↓                                   ↓
⑤ 自主执行动作                        ⑥ 转人工：附原因/证据/建议动作/已排除项
       ↓                                   （数据库域一律走这条，只出方案）
⑦ 验证（按动作自带的验证标准 + 时限）
   ├─ 恢复 → ⑧
   └─ 未恢复 → 停止，不再试第二个动作，转人工并说明「修了但没好」
       ↓
⑧ 结论回写告警 + 通知 + 知识沉淀
```

---

## 四、告警内容规范（第 ③ 步）

每条告警必须含以下字段，缺一视为不合格：

| 字段 | 示例 |
|---|---|
| 现象 | `qa-bgs/eft-gateway 4 个 Pod 全部 CrashLoopBackOff` |
| 时间 | `首次出现 06:39，持续 42 分钟` |
| 原因 | `新版本 :91 启动脚本首行被 -e 污染，容器启动即退出` |
| 证据 | `崩溃日志「line 1: -e: command not found」；revision 109-112 均 desired=0/ready=0；:82 版本同期正常` |
| 把握度 | `高（85%）` |
| 已做的处置 | `已回滚至 :32，服务恢复 1/1`（或「待人工确认」） |
| 影响面 | `影响 A 系统下单接口，约 30% 请求失败` |

---

## 五、自主处置的三个必要条件（缺一不可）

| 条件 | 说明 |
|---|---|
| **有手段** | 动作库里有匹配的动作；没有 → 转人工 |
| **有把握** | 原因分析把握度 ≥ 阈值（默认生产 0.8 / 测试 0.6） |
| **无用户感知**（生产） | 见第六节判定表；判不准一律按「有感知」处理 |

> 测试环境：第 3 条可放宽（有感知也允许自主执行，但要报备）。

---

## 六、用户感知判定（可计算，不靠感觉）

### 无用户感知（agent 可自主，生产也免审批）

同时满足全部：
- 副本数 ≥ 2
- 更新策略为滚动更新（RollingUpdate，且 maxUnavailable 不导致可用副本降到 0）
- 有就绪探针（readinessProbe）
- 执行期间始终 ≥1 个就绪副本在线
- 非缩容、非节点操作

典型动作：多副本 Deployment 回滚、多副本滚动重启、重建单个 Pod、补镜像拉取凭据、摘掉异常副本。

### 有用户感知（生产必须人工确认）

任一命中即是：
- 单副本工作负载的任何重启/回滚
- 无就绪探针（流量会立刻打到未就绪容器）
- 一次性重启全部 Pod（非滚动）
- 缩容 / 大规模扩容（超 2 倍）
- 有状态服务（StatefulSet）单点实例
- 节点操作（cordon / drain / 重启）
- 改探针或改配置导致的滚动重启
- **数据不足无法判定** ← 一律按此处理

### 数据库域

无「感知」判定，因为**从不执行**：只出方案（SQL + 回滚 SQL + 验证 SQL + 影响面），审批后 DBA 执行，平台记录结果。

## 七、与现有实现的差异（必须改的 4 处）

| # | 现状 | 目标 | 落点 |
|---|---|---|---|
| 1 | CrashLoop 先盲试一次「删 Pod 重建」，失败才分析 | **先分析**，原因清楚了再决定是否重建 | `alert_auto_service.py` `_try_rebuild_once` 调用点前移条件 |
| 2 | 崩溃日志命中代码特征 → 跳过分析直接转人工 | **先分析**，产出代码位置与引入版本后再转人工 | `alert_auto_service.py:1477` `_match_app_crash` 分支 |
| 3 | 重启整个服务无审批直接执行 | 生产按 Sixth 节判定，有感知必须人确认 | `alert_auto_service` 执行前闸门 |
| 4 | 告警在分析前发出，内容不含原因 | 两段式：先发「正在分析」，分析完补发结论 | 告警创建与通知链路 |

## 八、验收口径（怎么算做到了）

| 验收项 | 标准 |
|---|---|
| 先分析后告警 | 抽查 20 条告警，100% 携带原因与证据（分析失败的需含已排除项） |
| 自主解决 | 20 个历史故障回放，能自主解决 ≥ 8 个，且**无一造成二次故障** |
| 禁止盲试 | 自动执行的每条动作，日志中必须能查到对应原因分析（无原因即违规） |
| 用户感知判定 | 单副本服务触发重启时，100% 走审批；多副本滚动操作 100% 免审批 |
| 失败停手 | 构造验证失败场景，agent 停止且如实报告「修了没好」 |
| 转人工质量 | 转人工的单据必须含原因/证据/建议/已排除项，缺一视为失败 |

---

## 九、指标口径

- 应用域：自动解决率、MTTR、误操作率（改错配置/误回滚）、转人工单据完整率
- 数据库域：定位准确率、方案采纳率、人工节省时间
- 反指标（出现即需复盘）：无原因自动执行、连续试错、该转人工却自动执行
