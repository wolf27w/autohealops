## 二、S1 决策（老板未逐条回复，按合理默认落地，汇报里说明）

| 决策点 | 取值 | 理由 |
|---|---|---|
| 采集方案 | **A：`performance_schema.events_statements_history_long`** | 字段最全（耗时/锁等待/返回行数/扫描行数/HOST/USER/THREAD_ID/SCHEMA 全有），不改库表结构；B（`mysql.slow_log` 表）需要 `log_output=TABLE` 写表开销与额外授权 |
| 保留期 | **7 天** | 避免再造一张千万行表；每日清理任务 |
| 采集阈值 | 沿用连接级 `slow_sql_threshold`（默认 1s） | 与现有 digest 采集口径一致 |
| 采集频率 | 30 秒一次（仅捞 `TIMER_WAIT > 阈值`） | 与 digest 采集（60s）错开，避免同一窗口重复扫 |
| 范围 | 先只做 **MySQL**；PG/Oracle 明细留空并标注「该实例类型暂不支持明细」 | PG 无逐次历史（需 log_min_duration_statement + 日志解析），Oracle 需 AWR |
| 标签 | 本轮不做（S2） | 需要新表 + 打标入口，优先级低于明细本身 |

接口契约（前端按此开发）：

```
GET /api/v1/db-connections/{conn_id}/slow-sql-events
  query: start, end (ISO), schema, host, user, keyword, min_seconds,
         order=time|exec|rows_examined (默认 time), digest, page=1, page_size=50
  data: {
    total: int,
    items: [{
      id, digest, sql_text, schema_name, start_time (ISO),
      exec_seconds, lock_seconds, rows_sent, rows_examined,
      client_host, db_user, thread_id, tables (逗号分隔), tag
    }],
    supported: bool,        // 该连接是否支持明细（mysql=true）
    note: string            // 不支持时的说明
  }

POST /api/v1/db-connections/{conn_id}/slow-sql-events/collect
  → 手动触发一次采集 {collected: n}
```
