## 1. 批一 · 审核 / 人工协助闭环

1. **审核列表复用现有 `ApprovalList`**，同列表收两类单：高风险自动修复单 + 人工协助单（AI 诊断过、无法自动解决）。
   → `Approval` 加 `alert_id` + 类型标识（`kind=risk_approval / manual_assist`）；人工协助单允许无 `plan`。
2. **状态迁移**：高风险待审批 + 人工协助 → **都移出告警列表**，只在审核列表处理；处理完回「已解决」。
3. **审批人规则**：
   - **审批 ≠ 处理**（两个动作）：审批人批单，处理人执行，互不等同。
   - **非高风险**：不走审批，**值班人直接处理**（值班人即处理人）。
   - **高风险**：**双人审批 = 项目管理员 + admin**，**都批才通过**；无项目管理员 → 仅 admin。
   - **值班人不参与审批**（只接通知 + 处理非高风险单）。
   - 项目管理员 = 该告警「集群 + namespace」的管理员（项目成员 `manager`）。
4. **处理人** = 直接操作执行并确认的人（≠审批人）；审核单详情展示完整审批流程；处理记录页加「处理人」列。
5. **通知群来源**：**告警策略 `AlertPolicy`** 加「通知渠道」字段关联**通知配置 `notification_configs`**；通知发该群并 **@值班人员 + 审批人员**；未配置 → 只站内。
6. **站内消息中心**：右上角（铃铛 + 未读 + 列表 + 已读）；**走 IM 时同时写站内**。
7. **IM 通知模板**：通知配置里加「IM 通知模板」，**字段按渠道分别配置**（钉钉/企微/飞书各一套字段/占位符，附预置模板，用户可选用并自定义）。

## 2. 批二 · 体验优化

1. **AI 诊断助手提速**：命中知识库（已闭环）→ 直接复用历史方案、不走 AI；新会话默认**单轮**（平台预采集 describe/日志/进程 → 一次拼 prompt → 结论）；多轮取证收成可选「深度诊断」开关。
   - 现状「多轮」= AI 主动调只读工具取证、每次结果喂回 AI，最多 12 步（`agent_service.MAX_TOOL_STEPS=12`），慢在此。
2. **命名空间加载提速**：前端走 `/resources/clusters/{id}/namespace-list`（`resource_snapshots` distinct）；拟加 `(cluster_id, namespace)` 联合索引 / Redis 短缓存 / 预取（需实测定位）。
3. **左侧菜单可展开/收起，默认收起**（antd `Sider collapsible` + 记忆折叠状态）。
4. **自动刷新**：仪表盘、告警列表、审批列表定时轮询（10~15s）+「自动刷新」开关（如需更实时可 SSE/WebSocket）。
5. **「AI 配置」页合并**：「AI 模型」+「提示词模板」合成一页：Tab = 模型配置 / 提示词模板 / 调用日志。

## 3. 批三 · 状态检测补全与自动处置

1. **`TerminatingStuck`**：Pod 卡 Terminating 满 **60s** → 告警；告警后 **60s** → 自动强删（`delete pod --force --grace-period=0`）；**不分生产/测试、免审批**。
2. **状态检测补全**：容器级 + Pod 级异常状态**全部补齐**；节点级缺口一并补（含周期扫描，因为 cordon/水位不发事件）。
3. **处置四档**：🟢 自动 ／ 🟡 强删重建→观察→转人工 ／ 🔵 AI 诊断→修/转人工 ／ 🟠 转人工。
4. **「强删重建」仅删 Pod（控制器自动重建），绝不删节点**；节点类只告警+转人工。
5. **与专项 D 的边界（重要）**：本节「强删重建」= **异常 Pod 的自动自愈**（系统执行、免审批）；专项 D「重新创建服务」= **人工对工作负载的操作**（生产双人审批）。二者不同层、不冲突。

**检测覆盖现状**
- Pod 已覆盖：`CrashLoopBackOff` / `OOMKilled` / `ImagePullBackOff`+`ErrImagePull` / `PendingTimeout` /（新增）`TerminatingStuck`。
- 容器级缺口：`CreateContainerConfigError`、`CreateContainerError`、`RunContainerError`、`ContainerCannotRun`、`InvalidImageName`、`ErrImageNeverPull`、`RegistryUnavailable`、`ImageInspectError`、Init 容器失败、探针失败、`ContainerCreating` 卡住、重启增长未到 CrashLoop。
- Pod 级缺口：`Evicted`、`FailedScheduling/Unschedulable`、`FailedMount/FailedAttachVolume/FailedUnMount`、`FailedCreatePodSandBox`、`Unknown`、`Ready` 长期 False。
- Node 已覆盖：`NodeNotReady` / `MemoryPressure` / `DiskPressure` / `PIDPressure`。
- Node 缺口：`NetworkUnavailable`、`unreachable` 污点/心跳丢失、cordon 长期未恢复、pressure 污点长期、`KubeletNotReady/KubeletSetupFailed`、节点水位（CPU/内存/磁盘）、`InvalidDiskCapacity/FreeDiskSpaceFailed`、节点重启、Allocatable 不足。

**处置分档（待老板最终确认后落）**
| 档 | 状态 |
|---|---|
| 🟢 自动 | `ImagePullBackOff/ErrImagePull`（补 secret）、`TerminatingStuck`（60s 强删）、`Evicted`（清理僵尸 Pod） |
| 🟡 强删重建→观察→转人工 | `CreateContainerError/RunContainerError/ContainerCannotRun`、`ContainerCreating` 卡住、`FailedCreatePodSandBox`、`PendingTimeout`、`FailedScheduling/Unschedulable`、`FailedMount/FailedAttachVolume`、`Unknown`、`RegistryUnavailable` |
| 🔵 AI 诊断→修/转人工 | `CrashLoopBackOff`、`OOMKilled`、`Init:*`、`CreateContainerConfigError`、探针失败、`Ready` 长期 False、重启增长 |
| 🟠 转人工 | `InvalidImageName`、`ErrImageNeverPull`、`ImageInspectError`、全部节点类 |

## 5. 专项 B · 云原生 RBAC（Impersonation）🟡 排期待定

**目标**：资源操作权限由 **Kubernetes RBAC** 管，平台只做身份/项目映射；终端/exec 天然受控，k8s audit 记录真实用户。

**身份映射**：用户 → `apiops:<username>`；项目/角色 → group `apiops:proj:<id>:<read|operate|manager>`；自动化 → `apiops:automation`。

**接入（添加 kubeconfig 时自动）**：
1. **能力探测**（能否 create RBAC + impersonate）；
2. **自动下发三档 ClusterRole**：`apiops-read / apiops-operate`（+pods/exec、logs、port-forward）/ `apiops-manager`（+delete/patch）；
3. **可选自举专用账号**：自动建 SA `apiops-platform` + token + binding → 切换到它（不再长期依赖 cluster-admin kubeconfig）；
4. **项目/成员变更 → 自动 reconcile RoleBinding（绑组）**。
- 权限不够 → 提示缺项，或降级为「平台权限 + 白名单」模式。

**接入凭证（集群管理员先 apply，最小权限 = 仅 impersonate + 采集读）**：
```yaml
kind: ClusterRole
rules:
- apiGroups: [""]  resources: ["users","groups","serviceaccounts"]   verbs: ["impersonate"]
- apiGroups: [""]  resources: ["namespaces","nodes","pods","services","events","pv","pvc"]  verbs: ["get","list","watch"]
- apiGroups: ["apps"]  resources: ["deployments","statefulsets","daemonsets"]  verbs: ["get","list","watch"]
```

**运行链**：api-server 透传登录用户身份 → executor 调 k8s 带 `Impersonate-User/Group`（client-go `rest.ImpersonationConfig`）→ k8s RBAC 判定。采集用平台账号本身；AI/自愈用 `apiops:automation`。

**兼容**：已接入集群可按需逐步启用；**建议排批一之后**（专项 A 落"项目成员三级+项目管理员"，顺势映射 k8s 组）。

## 7. 专项 D · 集群管理云原生改造 & 容器终端 ✅

**需求**：用云原生视角管理集群——**去掉一级「Pod」Tab**，改走「无状态 / 有状态 / 定时任务 → 点服务 → 进服务详情（含 Pod 监控/YAML/终端/探针/回滚/重新创建）」；「进容器」= 真交互式终端。

**① 集群详情（改造）**：Tab = 无状态(Deployment) / 有状态(StatefulSet) / 定时任务(CronJob)（可加 DaemonSet）；**去掉 Pod Tab**；服务行 → 点入「服务详情」。

**② 服务详情页（新增）**：
- 概览：副本/就绪、镜像、状态、**副本增减（+/-）**、**探针（可视化编辑）**；
- **探针便捷编辑**：表单化（Liveness/Readiness/Startup：httpGet/tcpSocket/exec + 路径/端口 + initialDelay/period/timeout/阀值），保存即 patch，无需手写 YAML；
- **Pods 列表**：每行 监控 / 日志 / **进入终端** / YAML；
- 服务级操作：**回滚（选历史版本** `rollout history`→`undo --to-revision=<n>`）、**重新创建服务**、编辑 YAML。

**重新创建服务**：
- **无状态** → 删除重建整个工作负载（**先创建后删除**：先起新的 → 等 Pod 全 Ready → 删旧，判据 = Pod 就绪）；
- **有状态 / 用 PVC 的** → **滚动更新或原地重建**（不起两套、避免卷冲突）。

**审批规则（按环境）**：**生产环境**：副本增减 / 探针编辑 / 重建 / 回滚 → **走审批（双人 = 项目管理员 + admin）**；**其他环境直接执行**。（环境按 `Cluster.env_tag` 判定；副本**允许降到 0**）

**③ 从别处落到 Pod**：告警/其它入口点 Pod → 反查所属服务 → 跳服务详情对应 Pod（去掉 Pod Tab 也不丢入口）。

**④ 交互式终端链路**：`xterm.js` + WebSocket（浏览器↔api-server）+ executor **新增 bidi exec（TTY，stdin/stdout/resize）**（client-go remotecommand）；现状 `ExecInPod` 是单命令无 TTY。

**后端要补**：列出「工作负载→Pods」（现有 Deployment 的，需补 StatefulSet/DaemonSet/CronJob）；`rollout undo/restart` 直调；探针编辑（patch deployment）；交互式终端。

**安全（结论）**：**终端默认开**；k8s `pods/exec` 原生就是任意命令、无法白名单（KubeSphere 等同样直包 exec + 用 k8s RBAC 管）；平台靠 **RBAC + 命令审计**；只读白名单是给 **AI 自动诊断链路**防注入的补丁，**只管自动路径**，与人终端分开。

**状态**：✅ 定稿。**前端引入 `xterm.js`**（+ `xterm-addon-fit`），随项目构建、不影响环境；终端**默认开**；可用人按**平台 RBAC**；命令**审计留痕**。
