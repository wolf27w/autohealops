# 告警循环抑制与升级方案

> 状态：**方案确认中**（2026-08-20 老板讨论定稿，待开发）
> 背景：平台出现"同一 Pod 反复报警 → 自动处理（删Pod/补secrets）→ 恢复 → 又故障 → 又报警"的循环（实测：OOMKilled resolved 82 条、CrashLoopBackOff 35 条，同一资源重复 4-6 次）。根因：平台处理的是症状，应用层根因（内存配置/镜像认证等）未解决，Pod 重建后必然复发。

## 老板拍板的决策（2026-08-20）

1. **报警风暴抑制**：同一个报警 2 分钟内出现 5 次以上 → 不再频繁报警（防风暴）
2. **诊断方向修正**：镜像类故障（ImagePullBackOff/ErrImagePull）是**镜像认证问题不是服务问题**，诊断方向要正确——不走 AI 服务诊断，规则化处理
3. **升级人工**：5 分钟内出现 5 次 → 通知人工排查

## 一、同源告警定义

```
集群 + namespace + Deployment名（从 Pod 名推断，去掉随机后缀）+ 故障类型
```

- ⚠️ 不能按 Pod 名聚合：Pod 重建后名字带随机后缀（如 `eft-module-report-7f658474c9-8kvh9`），会漏掉
- 用现有 `infer_deployment_name`（Pod 名去掉 `-{rs-hash}-{pod-hash}` 后缀）

## 二、报警风暴抑制（2 分钟 / 5 次）

```
同源告警在 2 分钟窗口内 ≥5 次：
  → 不再新建 alert / 不再通知
  → 合并到现有告警的 event_count（计数累积）
```

- watcher createAlert 增强：同源聚合窗口从"不限时间"改为"2 分钟滚动窗口"
- 2 分钟内计数达到阈值 → 后续事件只累加 event_count，不重复通知

## 三、镜像类故障规则化（不走 AI 诊断）

ImagePullBackOff / ErrImagePull **不调 AI 服务诊断**，直接规则化处理（复用现有 `repair_image_pull`）：

```
镜像拉取失败
  ├─ 集群内有正常服务的 imagePullSecrets → 对比缺失 → 补上 → 恢复
  ├─ 集群内无其他 secrets → 无法自动补 → 转人工（镜像仓库认证配置）
  └─ secrets 已齐全仍失败 → 镜像名错/凭证失效/网络问题 → 转人工
```

- 现有 repair_image_pull 已实现上述判定（含"secrets 已一致仍失败→转人工"）
- 省掉无效的 AI 诊断调用，方向正确

## 四、升级人工（5 分钟 / 5 次）

```
同源告警 5 分钟窗口内 ≥5 次（自动处理了 5 次仍复发）：
  → 停止自动处理（标记该资源故障"已转人工"）
  → 通知值班人排查
  → 后续同源告警不再自动处理，只累积计数
```

- 判定"自愈无效"：说明是应用/配置根因问题，平台处理不了
- 转人工后引导诊断中心做应用/数据库诊断

## 五、实现位置

| 组件 | 改动 |
|---|---|
| k8s-executor watcher（Go）| createAlert 去重聚合改 2 分钟滚动窗口 + 风暴抑制（≥5 次合并计数不通知）|
| api-server alert_auto_service（Python）| 5 分钟 5 次判定 → 转人工 + 通知值班人（复用 `_mark_manual_and_notify`）|
| api-server alert_auto_service | 镜像类故障跳过 AI 诊断（直接规则化 repair_image_pull）|

## 六、与现有机制的关系

- 现有"pending 去重聚合（不限时间窗口）"→ 改为 2 分钟滚动窗口 + 抑制阈值
- 现有"观察期/重启≥3次"机制保留（A 类故障检测层不变）
- 通知限频（30 分钟）保留，风暴抑制是更早一层
